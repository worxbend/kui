## Connection-time URL policy (finding 25)

`HttpTls.resource(tls, policy)` is the production upstream transport factory. Composition roots pass the same immutable URL policy used to validate configuration and construct `UpstreamClient`. A strict pool must not be reused as a development pool or vice versa. Tests that intentionally bind loopback explicitly pass `UrlPolicy.Dev`.

The Blaze connection resolver obtains a single DNS answer set, rejects an empty set or **any** prohibited address, and returns a resolved `InetSocketAddress` containing the selected numeric address. The socket factory connects that exact address. No hostname is handed back to a second resolver. New connections repeat this check; pooled connections retain the peer that was already checked. The original request authority remains unchanged for HTTP Host, TLS peer-name verification and SNI. Custom JKS/PKCS12 trust replacement and client-key configuration continue to use the existing JSSE `SSLContext`.

Redirects are disabled at both the transport wrapper and resilient upstream layer. Proxy environment variables/JVM proxy selectors are not inherited by this direct transport, because a remotely resolving proxy would invalidate the local connection guarantee. Authentication remains in the existing request/credential layers.

### Versioned source decision

- sttp 4.0.26 [backend dependencies](https://github.com/softwaremill/sttp/blob/v4.0.26/build.sbt) and [Http4sBackend](https://github.com/softwaremill/sttp/blob/v4.0.26/http4s-backend/src/main/scalajvm/sttp/client4/http4s/Http4sBackend.scala) specify http4s-client 0.23.36 and optional Blaze 0.23.17.
- Blaze 0.23.17 [Http1Support](https://github.com/http4s/blaze/blob/v0.23.17/blaze-client/src/main/scala/org/http4s/blaze/client/Http1Support.scala) connects the resolver's address but creates `SSLEngine` from the original `RequestKey` and sets endpoint identification to `HTTPS`.
- Blaze [ClientChannelFactory](https://github.com/http4s/blaze/blob/v0.23.17/core/src/main/scala/org/http4s/blaze/channel/nio2/ClientChannelFactory.scala) connects the supplied socket address without resolving the authority again.
- The existing JDK HttpClient FS2 backend has no per-client DNS/socket-destination injection API. Checking DNS separately would leave TOCTOU; replacing the URI hostname with an IP would change TLS identity.
- Ember 0.23.36 was inspected but rejected: [`withSocketGroup` is a no-op](https://github.com/http4s/http4s/blob/v0.23.36/ember-client/shared/src/main/scala/org/http4s/ember/client/EmberClientBuilder.scala), and in the pinned [FS2 3.13.0 `NetworkPlatform`](https://github.com/typelevel/fs2/blob/v3.13.0/io/jvm/src/main/scala/fs2/io/net/NetworkPlatform.scala), `forAsyncAndDns` ignores its DNS argument. `Network` is sealed. Those apparent hooks do not enforce this policy.
- sttp's [Armeria FS2 backend](https://github.com/softwaremill/sttp/blob/v4.0.26/armeria-backend/fs2/src/main/scala/sttp/client4/armeria/fs2/ArmeriaFs2Backend.scala) is another resolver-capable option, but introduces Armeria and Netty TLS adaptation rather than reusing the existing JSSE context.
- sttp 4.0.26 [Http4sBackendBase.send](https://github.com/softwaremill/sttp/blob/v4.0.26/http4s-backend/src/main/scala/sttp/client4/http4s/Http4sBackendBase.scala) detaches its response fiber. `HttpTls` supplies an adapter-local `Async` whose `start` registers that fiber with a resource-owned Cats Effect supervisor and atomically records request cancellation before allowing it to run. Other primitives delegate to the original `Async` (including `racePair`, so structured races keep their normal ownership). This replaces the former extra exchange-owner bridge: the adapter's own response fiber now owns acquisition, body lifetime, release and the admission permit. Canceling or timing out `send` cancels and joins that fiber; backend resource release cancels and joins all supervised responses, including never-consumed unsafe bodies. The close signal also fails callers waiting on sttp's private response Deferred.

### Capacity, cancellation and response lifetime

`HttpTls.resource(tls, policy, HttpTls.Capacity(finite = 10, streaming = 10, queuedPerPool = 256))` exposes explicit budgets. These are factory parameters, not new environment/configuration keys. Existing composition roots use these defaults. Each backend has independent finite-response and streaming-response pools; default socket capacity is therefore at most 20, not an unbounded pool. A saturated streaming pool cannot consume the finite pool's ten reserved slots. Additional calls wait cancelably within their own budget, with at most 256 queued calls per pool; excess calls fail with a fixed queue-full error. `queuedPerPool = 0` provides fail-fast admission.

Routing uses sttp's [versioned response algebra](https://github.com/softwaremill/sttp/blob/v4.0.26/core/src/main/scala/sttp/client4/ResponseAs.scala), not URL paths, headers, request-body streaming capabilities, or a cast of the result body. Safe and unsafe FS2 response handlers both use the streaming budget. Mapped, metadata-conditional, and combined response descriptions are inspected recursively. Any possibly streaming metadata branch reserves streaming capacity before headers are known; a finite/error branch releases it normally. An upload with a finite response does not take a streaming slot merely because its request body streams.

Two [Cats Effect 3.7.1 semaphores](https://github.com/typelevel/cats-effect/blob/v3.7.1/std/shared/src/main/scala/cats/effect/std/Semaphore.scala) per pool bound outstanding calls and active exchanges. The active `permit` resource uses cancelable acquisition **before** Blaze's masked borrow, retaining its permit until the underlying response resource closes. Blaze's total and per-authority limits both equal that pool's active budget, and its internal wait-queue limit is explicitly zero. [PoolManager.borrow](https://github.com/http4s/blaze/blob/v0.23.17/blaze-client/src/main/scala/org/http4s/blaze/client/PoolManager.scala) can evict idle connections for other authorities when necessary, so admitted exchanges do not need its non-cancelable internal wait queue. The former defaults of ten shared sockets and a 256-entry internal callback queue are not used.

[Supervisor 3.7.1](https://github.com/typelevel/cats-effect/blob/v3.7.1/std/shared/src/main/scala/cats/effect/std/Supervisor.scala) is finalized before either Blaze pool. Live-socket regressions verify ten held responses plus a successful finite request on the same authority/path; bounded queued admission and zero-queue rejection; cancellation/timeout with no later network dispatch; EOF and consuming-stream cancellation returning permits; safe/mapped/conditional responses; and shutdown of active, queued and unconsumed responses with zero remaining owned response fibers and all permits restored. Negative regressions were observed before the fix: finite-call timeout at ten held streams, and shutdown leaving ten sockets plus one queued Blaze callback.

### Deliberate limits

- This is an application-level direct-peer policy, not an egress firewall: routing/NAT, transparent proxies, tunnels, and a permitted server forwarding requests are outside its visibility. Deploy network egress restrictions as defense in depth.
- Internal address access is still explicitly enabled by the existing `KUI_ALLOW_PRIVATE_UPSTREAMS=true` policy. That relaxation intentionally permits loopback/private destinations; no per-host allowlist is introduced.
- Mixed public/private DNS answers fail closed. Only the first address in an entirely permitted answer set is selected; there is no Happy Eyeballs/address-family fallback within that answer. Configured endpoint failover remains available.
- The system/JVM resolver may cache answers and a blocking OS name lookup is not forcibly interruptible. There is no separately trusted preflight DNS cache, and no new socket can use an unchecked answer.
- Blaze is HTTP/1.1 and this factory returns `StreamBackend`, not WebSocket capability. KUI's upstream consumers use HTTP and FS2/SSE, not WebSockets.
- Blaze 0.23.17 can emit asynchronous `Dispatcher already closed` diagnostics from idle-read callbacks during pool teardown. The live tests verify socket cancellation and refusal of requests after resource release; no delay or log-suppression workaround hides the upstream teardown diagnostic.
- Capacity is per backend instance and per response class, not per endpoint or tenant. The streaming budget remains finite: an eleventh default long-lived stream waits until one ends, but cannot block finite RPC capacity. A peer that never ends a response requested with a finite response handler can occupy a finite slot until its deadline/cancellation. This is response-shape isolation, not a promise to predict the remote server's behavior.
- Callers must consume or cancel unsafe response bodies to return capacity promptly; an abandoned body retains its slot until backend resource release. Resource release now closes even these abandoned exchanges. Non-cooperative user response callbacks, OS DNS, and Blaze's masked *new-connection establishment* can delay cancellation/shutdown; this change removes the masked **pool-wait** path, not JVM/OS blocking. `readTimeout` cancellation joins cleanup rather than abandoning such work.
- sttp's http4s backend does not implement per-request `readTimeout`, so `HttpTls` enforces it around `send` and propagates timeout cancellation to the active exchange. For an unsafe streaming response this bounds acquisition; after the stream is handed to its caller, the caller owns its lifetime/cancellation. KUI's existing upstream whole-call and OAuth operation deadlines remain in place.
